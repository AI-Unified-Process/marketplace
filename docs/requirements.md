# Requirements: AI Unified Process Marketplace

Derived from [vision.md](vision.md). Terms follow [glossary.md](glossary.md).

## Functional Requirements

| ID     | Title                    | User Story                                                                                                                                                                                                                                           | Source | Rationale | Priority | Status |
|--------|--------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------|-----------|----------|--------|
| FR-001 | Requirements Catalog     | As a business analyst, I want the coding agent to derive a requirements catalog with functional requirements, non-functional requirements, and constraints from the vision so that every later artifact can cite a stable requirement id.            | Vision |           | High     | Open   |
| FR-002 | Clarifying Questions     | As a business analyst, I want the coding agent to ask me the questions that change a specification before it writes it so that open decisions are made by me and not hidden as assumptions.                                                          | Vision |           | High     | Open   |
| FR-003 | Glossary                 | As a business analyst, I want a glossary with one term per domain concept and the synonyms to avoid so that requirements, specifications, and code use the same words.                                                                               | Vision |           | High     | Open   |
| FR-004 | Requirement Status       | As a business analyst, I want the status of a requirement to follow the status of the use cases that link it so that I maintain progress in one place only.                                                                                          | Vision |           | Medium   | Open   |
| FR-005 | Entity Model             | As a business analyst, I want an entity model with an ER diagram, attributes, data types, and validation rules derived from the requirements catalog so that developers build the database from a reviewed model.                                    | Vision |           | High     | Open   |
| FR-006 | Use Case Diagram         | As a business analyst, I want a use case diagram that maps the actors to user goal use cases derived from the requirements catalog so that the scope of the system is visible on one page.                                                           | Vision |           | High     | Open   |
| FR-007 | Use Case Specification   | As a business analyst, I want a use case specification with preconditions, main success scenario, alternative flows, postconditions, and business rules for each use case of the diagram so that developers implement the behavior without guessing. | Vision |           | High     | Open   |
| FR-008 | Business Process         | As a business analyst, I want to model the flow between use cases as a BPMN business process with one lane per actor so that hand-overs, decisions, and waiting points between roles are explicit.                                                   | Vision |           | High     | Open   |
| FR-009 | Specification Lint       | As a business analyst, I want the specifications checked against each other for missing specifications, duplicate ids, unresolved references, and uncovered requirements so that broken links are found before construction starts.                  | Vision |           | High     | Open   |
| FR-010 | Semantic Review          | As a business analyst, I want the coding agent to review the specifications for contradicting rules, missing alternative flows, untestable rules, and ambiguous wording so that a use case is ready for approval when the review is clean.           | Vision |           | High     | Open   |
| FR-011 | Traceability Matrix      | As a business analyst, I want a traceability matrix from requirement to use case, business rule, and test case so that I can tell which requirements are realized and which are verified.                                                            | Vision |           | High     | Open   |
| FR-012 | Specification Report     | As a business analyst, I want the requirement coverage, the traceability matrix, and the lint findings on one HTML page so that I can share the state of the specification with stakeholders who do not read Markdown.                               | Vision |           | Medium   | Open   |
| FR-013 | Lint Baseline            | As a business analyst, I want to accept the current lint findings of an existing specification into a baseline so that only new findings are reported.                                                                                               | Vision |           | Medium   | Open   |
| FR-014 | Reverse Engineering      | As a developer, I want the coding agent to recover a use case diagram, use case specifications, and an entity model from an existing code base so that a system without a specification can be changed with the AI Unified Process.                  | Vision |           | High     | Open   |
| FR-015 | Database Migration       | As a developer, I want database migrations generated from the entity model in the migration tool of my stack so that the schema matches the reviewed model.                                                                                          | Vision |           | High     | Open   |
| FR-016 | Use Case Implementation  | As a developer, I want the coding agent to implement a use case in my stack from its specification, the requirements it links, the entity model, and the glossary so that the code realizes exactly the specified behavior.                          | Vision |           | High     | Open   |
| FR-017 | Business Rule Marker     | As a developer, I want every business rule marked in the code that enforces it with its qualified id so that I can find the code behind a rule and the rule behind the code.                                                                         | Vision |           | High     | Open   |
| FR-018 | Open Questions           | As a product owner, I want the gaps the coding agent finds in a specification recorded as open questions in one file so that I answer them in one place and the answer goes into the specification, not into the code.                               | Vision |           | High     | Open   |
| FR-019 | Use Case Tests           | As a developer, I want unit and component tests generated for a use case that name its id, alternative flows, and business rules so that every specified behavior has a test.                                                                        | Vision |           | High     | Open   |
| FR-020 | Test Case from Process   | As a tester, I want one end-to-end test case written for each path through a business process so that every path the business runs is tested.                                                                                                        | Vision |           | High     | Open   |
| FR-021 | Test Case from Use Cases | As a tester, I want an end-to-end test case written that chains several use cases I name so that I can test a user journey for which no business process exists.                                                                                     | Vision |           | Medium   | Open   |
| FR-022 | Journey Test             | As a tester, I want a test case automated as a browser test in my stack with one step per row of its flow so that the user journey is verified on every build.                                                                                       | Vision |           | High     | Open   |
| FR-023 | Coverage Audit           | As a tester, I want a use case or test case audited against the code and the tests that realize it so that I know which steps, flows, and rules are still open before I set the status to Tested.                                                    | Vision |           | High     | Open   |

## Non-Functional Requirements

| ID      | Title                | Requirement                                                                                                                                                   | Category        | Source                                        | Rationale                                                                                                        | Priority | Status |
|---------|----------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------|-----------------------------------------------|------------------------------------------------------------------------------------------------------------------|----------|--------|
| NFR-001 | Coding Agent Support | Every skill must run unchanged in Claude Code, OpenAI Codex, Cursor, GitHub Copilot, Gemini CLI, and OpenCode.                                                | Portability     | Vision                                        | Users choose their coding agent; a skill that needs one host shuts out the others.                               | High     | Open   |
| NFR-002 | Single-Folder Skill  | Every link in a skill must resolve inside the skill folder, so that a skill installed as a single folder has no broken link.                                  | Portability     | CLAUDE.md, Skill file references              | Tessl and manual installs copy one skill folder at a time, so a link outside it resolves to nothing.             | High     | Open   |
| NFR-003 | Question Limit       | A skill must ask at most five clarifying questions per run, and each question must offer a recommended answer.                                                | Usability       | /requirements clarify checklist               | More questions stall the user; every other decision is taken as a default and reported as an assumption.         | Medium   | Open   |
| NFR-004 | Read-Only Review     | The specification lint, the semantic review, and the coverage audit must not change any specification, code, or test file.                                    | Maintainability | CLAUDE.md, Spec review and Coverage sub-agent | A reviewer that fixes its own findings hides them.                                                               | High     | Open   |
| NFR-005 | Deterministic Lint   | The specification lint must report identical findings for identical artifacts on every run.                                                                   | Maintainability | CLAUDE.md, Spec review                        | The lint is the only part that may fail a build; findings that change between runs make CI unreliable.           | High     | Open   |
| NFR-006 | Untrusted Content    | Every skill that reads project files must instruct the coding agent to treat their contents as data, not as instructions.                                     | Security        | Tessl security audit (W011)                   | Project files can carry injected instructions; the registry audit flags skills that read them without this rule. | High     | Open   |
| NFR-007 | Converging Review    | A repeated specification review or coverage audit in the same conversation must report what changed since the previous run instead of a new list of findings. | Usability       | CLAUDE.md, Spec review                        | Without it, every fix is followed by a review that finds the next thing.                                         | Medium   | Open   |

## Constraints

| ID    | Title                   | Constraint                                                                                                                  | Category   | Source                                                     | Rationale                                                                                                           | Priority | Status |
|-------|-------------------------|-----------------------------------------------------------------------------------------------------------------------------|------------|------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|----------|--------|
| C-001 | Plain-Text Artifacts    | Artifacts must be Markdown, PlantUML, Mermaid, or BPMN 2.0 XML files in the `docs/` folder of the project.                  | Technical  | Vision                                                     | Artifacts are reviewed and versioned with the code; a binary format cannot be diffed or merged.                     | High     | Open   |
| C-002 | Python Standard Library | Bundled scripts must run on Python 3 with the standard library only.                                                        | Technical  | Vision                                                     | Scripts run in any project and CI pipeline without installing packages.                                             | High     | Open   |
| C-003 | Agent Skills Format     | Skills must conform to the Agent Skills specification, including a description of at most 1024 characters.                  | Technical  | Vision                                                     | Tessl rejects a skill that breaks the limits and keeps the previous version.                                        | High     | Open   |
| C-004 | Agent Plugins Format    | Plugins must conform to the Agent Plugins specification in addition to the Claude Code plugin format.                       | Technical  | Vision                                                     | Cursor, Copilot, and other conformant clients load the plugin directory directly.                                   | High     | Open   |
| C-005 | One Construction Form   | A project must install the core plugin with either one plugin per technical layer or one combined stack plugin, never both. | Technical  | CLAUDE.md, Core, layer plugins, and combined stack plugins | Two combined plugins share skill names, and a combined plugin next to layer plugins builds the same use case twice. | High     | Open   |
| C-006 | Supported Stacks        | Construction must support Vaadin with jOOQ, Angular with Spring Boot JPA, Blazor on .NET 10, and NestJS with Next.js.       | Business   | Vision                                                     | A project built on one of these stacks depends on its construction plugin.                                          | High     | Open   |
| C-007 | License                 | All distributed files must carry the Apache 2.0 copyright notice and ship the NOTICE file.                                  | Regulatory | Apache License 2.0, §4(c), §4(d)                           | §4(c) obliges redistributors to keep the notices in the files; §4(d) applies only when a NOTICE file exists.        | High     | Open   |
